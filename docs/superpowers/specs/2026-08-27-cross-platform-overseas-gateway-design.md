# 跨平台海外专线接入网关设计

日期：2026-08-27  
状态：设计已确认，等待书面规范复核  
目标规模：约 100 名员工，其中约 30 名实际使用者

## 1. 背景与目标

公司使用电信提供的合法合规海外专线。现有专线客户端需要使用政府发放的 PIN 登录，且仅支持 Windows。项目目标是在内网部署一台 Windows Server 虚拟机作为统一出口，通过公司自研客户端，让 Windows、macOS、Linux 桌面和 Linux 服务器在获得授权后使用该线路。

员工首次使用时输入一次 AD 工号和密码完成注册；后续通过设备密钥自动认证并一键连接。电信 PIN 只存在于 Windows 网关，不下发给终端。

本项目不绕过运营商或主管部门的访问控制。所有出站访问仍受电信线路的站点白名单和既有合规机制约束。

## 2. 成功标准

- 支持 Windows、macOS、Linux 桌面和 Linux 服务器。
- 首次安装后 3 分钟内完成注册并连接；日常使用只需一次点击。
- 支持至少 20 路并发，满足约 30 名实际用户的使用规模。
- 连续运行 72 小时无异常断流、DNS 泄漏、IPv6 泄漏或普通互联网出口回落。
- AD 账号禁用或移出授权组后，在租约期限内自动失效。
- 电信客户端断线后，代理流量不得改走普通互联网出口。
- 卸载客户端后恢复原有 DNS、路由和防火墙状态。
- 注册、连接、拒绝、撤销和管理操作均可追溯到员工或服务器资产。

## 3. 已确认的架构决策

### 3.1 单 VM 部署

首版使用一台接入普通员工网段的 Windows Server VM，同时承载：

- Go 授权控制面；
- WireGuard 隧道端点；
- Windows 路由、NAT 和防火墙；
- 电信 Windows 客户端及 PIN 会话；
- 健康检查和审计采集。

首版接受单点故障：VM 故障时所有用户无法使用海外线路。未来可将接入控制面和电信出口拆分，或增加备用网关，但不属于首版范围。

### 3.2 WireGuard 全隧道

项目采用“自研客户端和授权控制面 + WireGuard 隧道引擎”。不自行实现 VPN 加密协议。

员工终端采用互联网全隧道：

- 企业内部网段保持直连；
- 其他 IPv4 互联网流量进入 WireGuard；
- IPv6 若未被专线完整支持，则在连接期间阻止互联网 IPv6 直出；
- DNS 按策略通过隧道解析，防止解析结果和审计链不一致。

Linux 服务器默认采用目标路由，只把获准海外 API、软件源、镜像仓库等目标送入隧道，避免改变默认路由导致 SSH、监控、备份或业务回包失联。经单独批准的服务器可以使用互联网全隧道。

### 3.3 自服务注册

不依赖 Endpoint Central 下发配置，也不需要管理员逐台配置。客户端安装后自行完成注册：

1. 客户端在本机生成设备密钥对。
2. 员工输入一次 AD 工号和密码。
3. 客户端通过 TLS 调用授权 API。
4. 服务端通过 LDAPS 临时验证凭据，并检查 `Overseas-Line-Users` AD 安全组。
5. 服务端登记设备公钥，分配隧道 IP 和策略。
6. 客户端获得短期设备凭证和连接租约。
7. 后续使用设备私钥签名自动认证，不再保存或重复使用 AD 密码。

Linux 服务器不使用员工账号注册，而使用管理员签发的一次性注册码换取主机身份。

## 4. 系统拓扑

```text

       | 设备注册、租约、状态（HTTPS）
       | WireGuard 全隧道（企业内网除外）
       v
+--------------------------------------------------+
| Windows Server VM                                |
|                                                  |
| gatewayd -> AD/LDAPS -> 设备/租约数据库          |
|    |                                             |
|    +-> WireGuard Peer 控制                       |
|    +-> 路由/NAT/防火墙                           |
|    +-> 健康检查/审计                             |

+--------------------------------------------------+
       |
       v
运营商/主管部门允许的海外站点

Linux servers
       | WireGuard 目标路由（默认）
       +-------------------------------------------> Windows Server VM
```

## 5. 组件边界

### 5.1 服务端

- `gatewayd`：Windows Service；对外提供授权、租约、状态和管理 API。
- `adprovider`：只负责 LDAPS 凭据验证、账号状态和安全组查询。
- `enrollment`：登记员工设备或服务器身份，实施设备数量限制。
- `lease`：分配隧道 IP、路由策略、租约和宽限期。
- `peercontroller`：增删 WireGuard Peer，读取握手与字节计数。
- `routecontroller`：管理 Windows IP 转发、NAT、静态路由、防火墙和防泄漏规则。
- `telcohealth`：监测电信客户端进程、线路接口、PIN 会话及获准测试目标。
- `audit`：生成结构化审计事件并转发到现有日志平台。
- `store`：SQLite 数据访问层；保存控制面状态，不保存 AD 密码或终端私钥。

### 5.2 客户端

客户端分为普通用户界面和高权限本机服务：

- UI：首次登录、连接、断开、状态、错误提示和设备注销。
- `clientd`：密钥管理、注册、租约续期、WireGuard、路由、DNS、防泄漏和恢复。
- UI 通过受限本机 IPC 调用 `clientd`；UI 不以管理员权限运行。
- 安装时允许出现一次管理员权限提示；日常连接不再提权。

平台实现：

- Windows：Go Windows Service，调用 WireGuard Windows 嵌入式组件和 Windows API。
- Linux：Go systemd Agent，通过 netlink/wgctrl 控制内核 WireGuard。
- macOS：Go 核心服务；用最薄的 Swift/Objective-C 桥接层调用 Network Extension、WireGuardKit 和 Keychain。
- Linux 服务器：复用 Go 核心，提供 `ovctl` CLI，不依赖 GUI。

## 6. API 与认证

首版 API：

- `POST /v1/enroll`：首次提交 AD 工号、密码、设备公钥和设备元数据。
- `POST /v1/session`：使用设备私钥对随机挑战签名，换取短期会话。
- `POST /v1/lease`：申请或续期 WireGuard 配置和路由策略。
- `POST /v1/revoke`：注销当前设备。
- `GET /v1/status`：查询授权、租约、网关和电信线路状态。

安全约束：

- API 只通过 TLS 提供服务；客户端校验企业 CA 和服务端名称。
- AD 密码仅存在于首次验证请求和服务端当次内存，不写日志、数据库或错误响应。
- 每台设备使用独立密钥；私钥永不上传。
- Windows 使用 DPAPI，macOS 使用 Keychain，Linux 使用仅 root 可读的文件或系统密钥环。
- 设备签名只证明已登记设备；服务端在续租时重新检查 AD 账号和安全组。
- 可以限制每名员工最多登记的设备数量，默认建议为 2 台。
- 管理接口与普通用户接口分权，所有管理操作写入审计。

## 7. 数据模型

- `users`：员工号、AD 标识、状态、最后验证时间。
- `devices`：设备 ID、公钥、操作系统、设备名称、员工绑定、状态。
- `server_identities`：资产编号、公钥、用途、负责人和状态。
- `leases`：隧道 IP、路由策略、签发时间、到期时间和宽限期。
- `peers`：WireGuard 公钥、最近握手、上传和下载字节数。
- `audit_events`：注册、连接、续期、撤销、拒绝和管理事件。
- `gateway_state`：电信客户端、PIN 会话、线路接口和探测结果。

数据库不保存 AD 密码、客户端私钥、HTTPS 正文或用户浏览内容。

## 8. 流量与防泄漏

Windows VM 必须保留以下静态直连路径：

- AD 域控和 DNS；
- 授权 API 自身所需的员工网段；
- 日志平台；
- 运维管理来源；
- WireGuard 监听地址。

只有来源为 WireGuard 地址池且符合策略的流量可以被 NAT 到电信线路。必须显式禁止这些流量从普通员工网卡默认网关出站。

状态转换：

- 电信线路健康：允许 WireGuard 地址池转发。
- 电信客户端断开、PIN 失效或健康探测失败：立即关闭转发，保留控制面状态查询。
- WireGuard 断开：终端恢复原有内网路由、DNS 和防火墙状态。
- 控制面短暂故障：已连接租约在有限宽限期内继续；到期后停止连接。
- VM 重启：先恢复电信客户端并通过健康探测，再开放转发。

## 9. 审计范围

默认记录：

- 员工号或服务器资产身份；
- 设备 ID、设备名称和操作系统；
- 注册、连接、断开、续期、拒绝和撤销时间；
- 分配的隧道 IP；
- 目标 IP、目标端口、协议和流量大小；
- DNS 查询日志；
- 管理员操作；
- 电信客户端、PIN 和线路状态。

本项目不进行 HTTPS 中间人解密，不采集 HTTPS 正文。域名与目标 IP 的关联只作为辅助审计，不声明为绝对准确映射。

## 10. 角色与权限

- 普通员工：注册本人设备、连接、断开和注销设备。
- Linux 服务器 Agent：仅使用主机身份和被分配的目标路由策略。
- 运维管理员：查看网关状态、维护 PIN 会话、断开异常连接。
- 安全管理员：维护 AD 授权组、查询审计、吊销员工、服务器或设备。
- 系统服务：修改 WireGuard、路由和防火墙；普通客户端不能直接调用管理接口。

## 12. 错误处理

- AD 密码错误：返回通用认证失败，不泄露账号是否存在。
- 无授权组：明确提示用户没有线路权限，并记录拒绝原因。
- 设备达到上限：提示先注销旧设备或联系安全管理员。
- 租约过期：停止海外流量，保留内网直连，并允许重新认证。
- WireGuard 无握手：区分端口不可达、密钥失配和系统服务异常。
- 电信线路异常：所有客户端看到统一的线路不可用状态，不无限重试。
- 路由或防火墙应用失败：回滚到连接前快照，并停止隧道。
- 卸载失败：保留恢复工具，确保可单独清理虚拟网卡、路由、DNS 和防火墙规则。

## 14. 实施阶段

### 阶段 0：流量可行性 PoC

先使用官方 WireGuard 工具，不开发完整 GUI：

1. Windows VM 登录电信客户端。
2. 测试终端连接 WireGuard。
3. 启用 Windows IP 转发和 NAT。
4. 验证被 NAT 的外部终端流量能否进入电信线路。
5. 验证允许站点、DNS、IPv6、大文件和并发流量。
6. 关闭电信客户端，验证不能回落到普通互联网出口。

只有 PoC 通过才进入产品开发。若电信客户端只允许本机进程流量或阻止转发，需要运营商提供网关模式、SDK 或客户端支持；上层客户端无法绕过该限制。

### 阶段 1：服务端 MVP

实现 AD 注册、设备身份、租约、Peer 自动管理、健康检查和审计。

### 阶段 2：员工终端

实现 Windows 和 macOS 安装包、首次登录、一键连接、自动恢复和卸载。先由 5 名员工试运行，再扩大至约 30 名。

### 阶段 3：Linux

先实现 Linux 服务器 CLI/Agent 和目标路由，再按实际需求增加 Linux 桌面 GUI。

### 阶段 4：运营商产品化

完善签名升级、版本回退、部署文档、配置备份、PIN 到期告警和可选高可用方案，形成可向运营商交付的成果。

## 15. 明确不在首版范围内

- 绕过运营商或主管部门白名单；
- HTTPS 解密和正文采集；
- 移动端 iOS/Android 客户端；
- 多地域、多租户和云管平台；
- 自动 PIN 登录或规避 PIN 人工认证；
- 双 VM 或双网关高可用；
- 以 Endpoint Central 作为必要依赖。

## 16. 实施前置门槛

电信客户端是否接受来自 WireGuard 地址池、经 Windows NAT 转发的流量尚未实测。这是唯一会直接否定当前技术路径的前置门槛，必须在任何完整客户端开发前完成验证。
